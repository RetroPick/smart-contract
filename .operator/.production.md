## Production Assumptions

RetroPick V1 is not a trustless protocol.

Security depends on both:

- the solidity code
- the people and systems controlling the privileged surfaces

Those privileged surfaces include:

- UUPS upgrades
- selector routing to delegatecall modules
- module code-hash allowlisting and registration
- oracle replacement
- yield-router replacement
- pause and unpause
- emergency recovery
- treasury withdrawal
- trusted-reporter rotation and correction

If operators are weak, the protocol is weak.

## Architecture Summary

### Core Architecture

The deployed system uses:

- a UUPS proxy rooted at `MarketEngineDispatcher`
- delegatecall modules for admin, view, user ops, core lifecycle, and rolling lifecycle
- Chainlink-family oracle adapters
- optional trusted-reporter adapter for reporter-settled markets
- optional yield router configured after deploy

### Practical Trust Boundary

The most important production fact is:

- the `admin` role is the real control plane

The `admin` can:

- upgrade the dispatcher
- allow and register modules
- rewire selectors
- change router and fee parameters
- change oracle adapters
- pause and recover balances

That means `admin` must be a Safe multisig from day one.

## Recommended Account Topology

Use separate production identities for separate functions.

### 1. Admin Safe

Purpose:

- owns all privileged engine actions
- owns upgrades and module governance
- owns emergency recovery

Recommendation:

- Safe on the target mainnet or L2
- `3-of-5` minimum for meaningful TVL
- all signers should use hardware wallets
- no signer should be a shared team browser wallet

Suggested owners:

- founder / protocol lead
- security lead
- operations lead
- independent technical signer
- treasury/governance signer

Threshold guidance:

- small guarded launch: `2-of-3` acceptable only temporarily
- real production: `3-of-5` preferred
- serious TVL: `4-of-7` can be justified if signer reliability is strong

### 2. Treasury Safe

Purpose:

- receives fee withdrawals
- isolates treasury custody from protocol admin custody

Recommendation:

- separate Safe from admin Safe
- `2-of-4` or `3-of-5`
- signer set should overlap only partially with Admin Safe

### 3. Worker / Keeper Key

Purpose:

- operational lifecycle execution
- lock / resolve / rolling tick work

Recommendation:

- not a Safe
- dedicated hot operational key
- funded minimally
- replaceable immediately by Admin Safe
- must not hold upgrade or treasury authority

### 4. Trusted Reporter Key

If trusted-reporter markets are used:

- the reporter signing key must be separate from governance keys
- the adapter owner should be Admin Safe
- the reporter private key must be treated as production oracle infrastructure

## Safe Setup Using Gnosis Safe / Safe

### Safe Creation

Create at least:

- one Admin Safe
- one Treasury Safe

Use the Safe web app for the target chain.

Required configuration:

1. Add all named owners.
2. Set the intended threshold.
3. Label every owner with a real-world role.
4. Record Safe address and creation transaction hash.
5. Store the Safe addresses in the deployment release record.

### Safe Policy Requirements

For production:

- all owners use hardware wallets
- no blind signing
- every signer independently validates destination, calldata, and chain
- Safe Transaction Service notifications must be enabled
- unknown modules or guards should not be enabled casually

Recommended practices:

- use separate signer devices from daily browsing devices
- maintain an owner roster and rotation procedure
- require internal written change requests for all high-risk Safe transactions

### Safe Transaction Classes

Define three classes internally:

`emergency`

- pause
- emergency withdraw
- trusted-reporter rotation after compromise

`planned high-risk`

- upgrade
- module registration
- selector rewiring
- router replacement
- oracle replacement

`planned medium-risk`

- treasury update
- worker update
- deposit executor changes
- cursor reset
- failure-state reset

Each class should have:

- required reviewers
- minimum waiting period
- required simulation
- required post-change validation

### Safe Signer Runbook

Every signer must independently confirm:

- correct chain
- correct contract address
- correct function selector
- correct parameter values
- whether pause is active or required
- whether the change ticket matches the transaction

Never sign:

- opaque raw transactions without decoded calldata
- selector rewires without a signed manifest
- module approval without the verified code hash
- upgrades without dry-run evidence

## Production Roles and Ownership Mapping

Recommended live ownership mapping:

- `ADMIN` = Admin Safe
- `TREASURY` = Treasury Safe
- `WORKER` = dedicated worker EOA
- `TrustedReporterAdapter.owner()` = Admin Safe
- `trustedReporter` = dedicated reporter key

This mapping is already supported by the deploy script configuration model.

## Mainnet Readiness Requirements

Before any mainnet deploy:

1. `forge fmt`
2. `forge build`
3. `forge test`
4. `forge test --gas-report`
5. dry-run deployment script on fork or target RPC without broadcasting
6. verify chain ID and env values
7. verify deployer keystore funding
8. verify Safe addresses and signer roster
9. verify module deployment artifacts and release manifest
10. verify monitoring stack is live before deposits are enabled

Additional organizational requirements:

- named incident commander
- named release owner
- named security reviewer
- named treasury reviewer

## Deployment Strategy

### Recommended Order

1. create Safe multisigs first
2. prepare env file with Safe addresses
3. dry-run production deploy
4. broadcast production deploy from controlled deployer keystore
5. validate deployed proxy and adapters
6. configure feed decimals and template set
7. optionally configure yield router later under controlled change
8. enable markets gradually

### Important Ownership Principle

The deployer should not remain privileged after deployment.

Set:

- `ADMIN` to the Admin Safe during initialization
- `TREASURY` to the Treasury Safe during initialization
- `WORKER` to the intended worker key during initialization

That way, the deployer only pays gas and does not become the long-term governance authority.

## Mainnet Deployment Procedure

### Step 1. Prepare the release

Create a release record containing:

- git commit hash
- compiler / Foundry version
- target chain
- env file checksum
- Safe addresses
- expected proxy and adapter artifacts
- signer approvals

### Step 2. Dry-run deployment

Use the production deployment script without broadcasting.

Example dry-run:

```bash
forge script script/production/DeployProduction.s.sol:DeployProduction \
  --rpc-url "$RPC_URL" \
  --ffi \
  --gas-limit 5000000 \
  -vvvv
```

The dry-run must verify:

- correct chain ID
- env loads correctly
- deploy script completes
- initialization succeeds
- module wiring succeeds
- post-deploy assertions pass

### Step 3. Check deployer balance

Before real execution:

```bash
cast balance <DEPLOYER_ADDRESS> --rpc-url "$RPC_URL"
```

The deployer must have enough native gas token for:

- adapter deploys
- proxy deploy
- module deploys
- module wiring
- post-deploy configuration txs inside the script

### Step 4. Execute mainnet deployment

Operational rule:

- use Foundry keystore
- do not pass raw private keys
- release owner and security reviewer must both confirm final env values

The actual broadcast command should be executed only after final signoff. Keep it outside reusable templates.

### Step 5. Record deployment output

Capture and archive:

- proxy address
- implementation address
- adapter addresses
- transaction hashes
- block number
- deployer address

The deploy script prints:

- `ChainlinkAdapter`
- `RateAdapter`
- `SmartDataAdapter`
- `MacroAdapter`
- `EquityAdapter`
- proxy
- implementation
- admin
- treasury
- worker

All of that should be copied into the release record.

## Post-Deployment Validation

Immediately after deployment, verify:

1. `configInitialized() == true`
2. `stakeToken()` matches intended token
3. `priceOracle()` matches deployed base adapter
4. `admin()` equals Admin Safe
5. `treasury()` equals Treasury Safe
6. `workerAuthority()` equals intended worker
7. rate/smartdata/macro/equity oracles match intended adapter addresses
8. module wiring completed successfully

Suggested `cast call` checks:

```bash
cast call <PROXY> "configInitialized()(bool)" --rpc-url "$RPC_URL"
cast call <PROXY> "admin()(address)" --rpc-url "$RPC_URL"
cast call <PROXY> "treasury()(address)" --rpc-url "$RPC_URL"
cast call <PROXY> "workerAuthority()(address)" --rpc-url "$RPC_URL"
cast call <PROXY> "stakeToken()(address)" --rpc-url "$RPC_URL"
```

Also verify:

- Safe owns admin role indirectly by being the `admin` address
- no deployer-only authority remains
- monitoring stack sees the deployment events

## Feed and Oracle Bring-Up

After deployment and before market activation:

1. configure Chainlink feed decimals on the adapter for each feed used
2. validate staleness and confidence policy per market set
3. if trusted-reporter markets will be used:
   - verify adapter owner is Admin Safe
   - verify `trustedReporter`
   - verify `maxSignatureAgeSeconds`

Do not launch templates before feed decimals and oracle assumptions are confirmed.

## Template Bring-Up

Before opening real markets:

1. initialize each template deliberately
2. review market timings and oracle kind
3. review allowed outcomes and fee configuration
4. confirm template class and oracle class match the intended market design
5. rehearse one test lifecycle off mainnet or with non-production capital

## Yield Router Bring-Up

The core deploy script does not require the yield router to be active from first block.

This is a feature, not a weakness.

Recommended policy:

- deploy engine first
- observe stable operation
- add yield router later under a controlled paused maintenance window

Before setting a yield router:

1. verify router deployment and bytecode
2. verify router asset support and path configuration
3. verify recovery assumptions and emergency unwind behavior
4. verify yield fee bps

Live rule:

- never replace a live router while `totalRoutedPrincipal != 0`

## Upgrade Procedure

Use:

- [script/production/UpgradeProduction.s.sol](/home/asyam/dev/Project/RetroPick/V1/contract/script/production/UpgradeProduction.s.sol:1)

The repo already uses OpenZeppelin upgrades tooling and validates storage layout with `--ffi`.

### Upgrade Preflight

Before any production upgrade:

1. pause protocol
2. run full test suite
3. dry-run upgrade script
4. validate unchanged critical storage values
5. review whether new selectors require rewiring
6. prepare rollback plan

Dry-run example:

```bash
PROXY_ADDRESS=0x... \
forge script script/production/UpgradeProduction.s.sol:UpgradeProduction \
  --rpc-url "$RPC_URL" \
  --ffi \
  --gas-limit 5000000 \
  -vvvv
```

### Upgrade Execution Policy

- the actual upgrade must be approved by Admin Safe governance policy
- if the live proxy owner is the Admin Safe, the final upgrade call must align with that control model
- do not treat upgrades as routine maintenance

### Upgrade Postchecks

Verify unchanged:

- `stakeToken`
- `priceOracle`
- `admin`
- `treasury`
- `workerAuthority`
- `configInitialized`

Then verify:

- implementation address changed as intended
- selector routes still map correctly
- read paths function correctly
- no module approval state changed unexpectedly

## Module Governance Procedure

This is the highest-risk operational surface in the protocol.

Before module allowlist / registration / selector changes:

1. pause protocol
2. verify source commit
3. verify bytecode reproducibility
4. verify code hash
5. verify storage compatibility assumptions
6. verify selector manifest
7. verify independent reviewer approval

Never:

- approve module bytecode from an unreviewed local build
- route selectors to a module that has not been hash-verified
- batch multiple unrelated selector rewires in one step

## Maintenance Program

### Daily

1. check admin, treasury, and worker addresses
2. check no unexpected router-disabled state
3. check no unexpected unreconciled recovery
4. check no unexpected module or upgrade events
5. check no unexpected trusted-reporter rotation or clear events
6. check no unexpected rolling halt

### Weekly

1. rotate worker funding if needed
2. review fee balances and treasury accounting
3. review alert logs
4. review signer roster health
5. review pending governance actions

### Monthly

1. test emergency pause workflow
2. review Safe owner set and signer health
3. review oracle matrix and market parameters
4. review incident log and false positives
5. review whether protocol limits should change

## Maintenance Windows

Use a maintenance window for:

- router changes
- oracle changes
- upgrades
- module changes
- trusted-reporter owner or reporter rotation where practical

Every maintenance window should include:

- reason for change
- expected state transition
- exact tx list
- expected emitted events
- post-change checks
- abort conditions

## Incident Handling

This document is not a substitute for the operational runbook.

Use:

- [.runbook.md](/home/asyam/dev/Project/RetroPick/V1/contract/.runbook.md:1)

Production policy:

- pause early
- recover conservatively
- never reconcile unrecovered balances
- never finalize recovered yield while routed principal remains outstanding
- never unpause while the system is still in a known-bad state

## Serious-TVL Production Policy

For serious TVL, all of the following should be true before calling the protocol production-ready:

1. Admin Safe is active and documented.
2. Treasury Safe is active and documented.
3. signer policy is written and enforced.
4. worker ops are monitored.
5. deployment record is archived.
6. module release policy is in place.
7. upgrade policy is in place.
8. router and oracle change policy is in place.
9. incident commander roster exists.
10. external audit and remediation tracking exist.

## Recommended Launch Phases

### Phase 1. Internal Launch

- small internal capital
- no public expectation of continuous uptime
- exercise manual operations
- verify alerts and runbook

### Phase 2. Guarded Pilot

- strict caps
- limited market set
- no experimental router or oracle changes
- signer process rehearsed

### Phase 3. Production Expansion

- only after stable pilot period
- only after maintenance and incident discipline is demonstrated
- only after governance and module controls are proven in practice

## Things Operators Must Never Do

- deploy with an EOA as long-term admin
- keep treasury as a hot wallet
- use raw private keys in deployment commands
- skip dry-runs before upgrades
- replace router with outstanding routed principal
- reset oracle cursors during active `Open` or `Locked` epochs
- allow unreviewed module hashes
- sign opaque multisig transactions without decoded calldata
- unpause because the UI appears normal

## Final Operator View

RetroPick V1 can be operated professionally, but only if the production discipline matches the power of the admin surface.

The right mental model is:

- this is not “set and forget”
- this is controlled financial infrastructure
- Safe governance, deployment hygiene, post-change validation, and incident handling are all part of the protocol itself
