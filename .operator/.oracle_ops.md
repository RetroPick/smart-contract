# RetroPick V1 Oracle Operations Guide

## Purpose

This document defines how oracle infrastructure should be operated for the current Base-mainnet-first deployment.

It covers:

- Chainlink-family adapter operations
- Base L2 sequencer considerations
- oracle replacement rules
- cursor-reset handling
- trusted-reporter operations
- reporter compromise and correction procedures

## Oracle Operations Principles

1. Oracle choice is part of market design.
2. Oracle replacement is a governance event.
3. Active epoch semantics should not be changed casually.
4. Reporter-settled markets are operationally heavier than Chainlink-family markets.

## Base Mainnet Oracle Assumptions

On Base, operators must account for:

- sequencer feed status
- sequencer grace-period behavior
- feed staleness
- confidence-wide samples

Operational implication:

- a lifecycle failure may be an oracle health issue, not a contract issue
- a rolling halt may be due to buffer miss, stale data, confidence-wide data, or sequencer-related problems

## Required Oracle Matrix

Maintain an internal matrix per template containing:

- template id and slug
- oracle class
- feed ids
- adapter address
- intended heartbeat and delay assumptions
- `oracleMaxDelaySeconds`
- `oracleMaxConfidenceBps`
- incident plan

No template should go live unless it exists in this matrix.

## Chainlink-Family Operations

Before enabling a feed:

1. verify feed address and decimals configuration
2. verify chain-specific availability on Base
3. verify acceptable staleness window
4. verify acceptable confidence policy
5. verify sequencer-feed assumptions for the chain

## Oracle Replacement

When replacing an adapter:

1. identify affected templates
2. determine whether pause is required
3. document whether active epochs continue under prior snapshot semantics
4. execute adapter replacement through governance
5. reset cursor only if needed and only for the affected template/feed pair
6. validate next lock/resolve behavior

Important rule:

- replacing an adapter is not the same as changing already-snapshotted epoch data

## Cursor Reset Rules

`resetOracleCursor(templateId, feedId)` is a sensitive maintenance action.

Allowed only when:

- admin governance approves it
- the reset is scoped to a specific template/feed pair
- the active epoch is not `Open` or `Locked`

Never use cursor reset as generic cleanup.

## Diagnosing Oracle-Related Lifecycle Failures

When lifecycle work fails, classify the cause before acting:

- **stale oracle**: feed freshness exceeded
- **confidence-wide**: sample exceeds configured confidence policy
- **sequencer issue**: L2 sequencer feed indicates down or grace-period restriction
- **buffer miss**: rolling operation missed its allowed timing window

Do not fix buffer misses with oracle changes, and do not fix oracle failures with rolling resets unless the actual root cause is known.

## Trusted Reporter Operations

Trusted reporter is a strong centralization point and must be treated as settlement-critical infrastructure.

Required roles:

- Admin Safe owns the adapter
- reporter key signs payloads
- oracle ops team manages the signing service

Reporter key requirements:

- dedicated key only
- isolated service or device
- audit log of signing activity
- never reused as governance or treasury key

## Trusted Reporter Correction Policy

Correction actions:

- `clearLockSample`
- `clearResolveResult`
- `clearOhlcResult`

Rules:

- every clear action requires a written incident or correction record
- clear only the minimal necessary artifact
- verify the emitted clear event
- repost corrected data only after human review

## Reporter Rotation

Use reporter rotation for:

- key compromise
- key retirement
- infrastructure migration

Required procedure:

1. create incident or governance ticket
2. pause affected markets if needed
3. rotate reporter through governance
4. verify rotation event
5. confirm downstream systems know the reporter epoch changed

## Reporter Compromise Procedure

If reporter compromise is suspected:

1. pause affected reporter-settled markets immediately
2. stop trusting unpublished or recently produced payloads
3. rotate reporter key
4. inspect affected lock/resolve/OHLC records
5. clear only incorrect data
6. repost corrected values after review
7. record the full incident timeline

## Monitoring

Monitor at minimum:

- oracle adapter replacement events
- cursor reset events
- rolling halts
- reporter rotation events
- reporter clear events

Treat every oracle adapter change, cursor reset, and reporter clear as a high-severity production signal.

## Final Policy

Oracle operations are settlement operations.

If the oracle control plane is weak, the market is not safe no matter how correct the core engine code is.
