# RetroPick V1 Module Release Checklist

## Purpose

This document defines the release process for **delegated modules** in the current V2 architecture.

It applies to:

- `MarketEngineViewModule`
- `MarketEngineCoreLifecycleModule`
- `MarketEngineRollingLifecycleModule`
- any future delegated module

It does **not** govern the direct admin/user surfaces implemented on `MarketEngineDispatcher`.

## V2 Scope Boundary

Operators must distinguish two classes of code change:

### A. Dispatcher-root change

Examples:

- UUPS implementation upgrade
- changes to direct admin selectors
- changes to direct user/claims selectors

This is an **upgrade event**, not a module release.

### B. Delegated module change

Examples:

- new view module build
- new lifecycle module build
- delegated selector remap

This is a **module release event** and follows this checklist.

## Release Artifacts

Every delegated module release must produce:

1. reviewed source commit hash
2. compiler and Foundry version
3. module path and module address
4. expected code hash
5. delegated selector manifest
6. reviewer approvals
7. deployment tx hash
8. allowlist tx hash
9. register tx hash
10. selector-routing tx hashes

## Mandatory Pre-Release Review

Before allowlisting or registering a module:

1. review the exact source diff
2. verify the module is intended to run against `MarketEngineState`
3. reproduce bytecode from the reviewed commit
4. compute the exact code hash
5. verify storage-compatibility assumptions
6. enumerate all delegated selectors that should map to this module
7. confirm no root-owned selectors appear in the selector manifest

## Delegated Selector Manifest

The release manifest must contain:

- selector hex
- function signature
- target delegated module
- immutable flag
- prior module, if replacing
- reason for change

This manifest must match `ScriptSelectorMatrix` and the release record.

## Release Procedure

### 1. Pause Decision

Default policy:

- pause before delegated selector rewiring or module replacement on production

If governance chooses not to pause, the exception must be written and approved.

### 2. Allowlist Code Hash

Through Admin Safe:

- call `allowModuleCodeHash(codeHash)`

Validation:

- correct event emitted
- code hash matches the release artifact

### 3. Register Module

Through Admin Safe:

- call `registerModule(module, expectedCodeHash)`

Validation:

- module approved
- stored code hash matches expected
- storage compatibility check passes

### 4. Route Delegated Selectors

Through Admin Safe:

- call `setSelectorModule(selector, module, immutableFlag)` only for delegated selectors

Validation:

- selector maps to intended module
- no unrelated delegated selectors changed

### 5. Post-Release Checks

Verify:

- operator/global view reads still work
- manual lifecycle functions still work
- rolling lifecycle functions still work
- no unexpected module approval or selector movement occurred

## Red Flags

Stop release immediately if:

- a root-owned selector appears in the module manifest
- bytecode cannot be reproduced
- source commit is not the reviewed one
- module hash differs from the release artifact
- signers are asked to approve opaque calldata

## Rollback Policy

Every module release must have one rollback path prepared in advance:

- remap delegated selectors to the prior approved module
- revoke the faulty module
- keep protocol paused during rollback

If the problem is in dispatcher-root code, use the upgrade process instead of trying to solve it with delegated module governance.

## Final Policy

Module governance is safe only when operators remember the V2 split:

**delegated modules are release-managed; direct root-owned selectors are upgrade-managed.**
