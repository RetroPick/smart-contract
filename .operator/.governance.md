# RetroPick V1 Governance and Change-Control Policy

## Purpose

This document defines how privileged control of the current V2 deployment must be exercised in production.

It covers:

- governance scope
- change classes
- approval standard
- emergency vs planned actions
- pause requirements
- unpause gate

## Governance Scope

Governance controls:

- UUPS upgrades
- module code-hash allowlisting
- delegated module registration and revocation
- delegated selector routing changes
- router replacement and failure-state reset
- oracle adapter replacement
- oracle cursor reset
- pause and unpause
- emergency recovery actions
- worker, treasury, and deposit executor changes
- market initialization
- fee withdrawal
- reporter rotation and correction ownership actions

These powers are protocol-custody-equivalent.

## Governance Structure

### Admin Safe

All privileged protocol changes must flow through the Admin Safe.

Minimum standards:

- no EOA admin in production
- hardware-wallet signers only
- documented signer roster
- documented threshold policy
- documented incident escalation path

### Treasury Safe

Treasury custody should be separated from Admin Safe whenever possible.

### Required Human Roles

Every non-emergency change should have:

- one change owner
- one independent technical reviewer
- one approving signer path through the Safe threshold

High-risk changes require two technical reviewers.

## Change Classes

### Class A: Emergency

Includes:

- pause
- reporter rotation after compromise
- `yieldEmergencyWithdraw`
- `reconcileEpochRoutedPrincipal`
- `recoverRoutedSettledClaims`
- `reassignRecoveredBalance`
- `finalizeRecoveredYield`

Policy:

- fastest safe signer path
- incident ticket still required
- post-incident review mandatory

### Class B: High-Risk Planned

Includes:

- UUPS upgrade
- delegated module allowlist / register / revoke
- delegated selector rewiring
- router replacement
- oracle adapter replacement
- rolling lifecycle reset

Policy:

- written change request
- dry-run or simulation evidence
- scheduled maintenance window
- explicit validation checklist
- rollback plan prepared before signing

### Class C: Medium-Risk Planned

Includes:

- worker change
- treasury change
- deposit executor updates
- oracle cursor reset
- failure-state reset
- reporter clear operations

Policy:

- written request
- decoded transaction review
- one technical reviewer minimum

### Class D: Routine Financial

Includes:

- fee withdrawals

Policy:

- accounting review
- treasury review
- threshold approval through the intended Safe path

## Pause Policy

Pause is required by default before:

- upgrades
- router replacement
- nontrivial oracle replacement
- major recovery actions
- delegated module rewiring on production

Pause should be triggered immediately for:

- router integrity uncertainty
- recovery-pending state
- settlement-source uncertainty
- governance key compromise suspicion
- unexpected selector/module/upgrade event

## Unpause Policy

Unpause requires all of:

- `totalUnreconciledRecovered == 0`
- `yieldRouterDisabled == false` if routing is expected
- all affected templates have `unsafeToUnpauseForTemplate == false`
- incident commander or change owner signs off
- technical reviewer signs off
- Safe threshold approval

Governance must not unpause just because a hot issue has quieted down. The state must be clean.

## Upgrade Policy

Upgrades are not routine maintenance.

Before upgrade:

1. full test pass on the release candidate
2. OpenZeppelin storage-layout validation
3. reviewed diff for dispatcher-root behavior
4. explicit note on whether any root-owned selector behavior changes
5. post-upgrade validation checklist

After upgrade:

- verify proxy still points to intended implementation
- verify config addresses unchanged
- verify root-owned behavior and delegated selector mappings both still match the release record

## Router Governance Policy

Before router replacement:

1. confirm `totalRoutedPrincipal == 0`
2. confirm new router artifact and deployment record
3. confirm intended `yieldFeeBps`
4. confirm emergency recovery assumptions
5. perform under pause

Never authorize router replacement while routed principal remains outstanding.

## Oracle Governance Policy

Before oracle replacement:

1. identify affected templates
2. confirm whether pause is required
3. evaluate active-epoch implications
4. decide whether cursor reset is necessary
5. document expected post-change settlement semantics

Never authorize broad cursor resets or ad hoc oracle changes without scoped rationale.

## Delegated Module Governance Policy

Before module governance actions:

1. distinguish delegated selector changes from root-owned behavior changes
2. verify code hash and source commit
3. confirm selector manifest contains delegated selectors only
4. confirm rollback path

Never use module governance to “fix” root-owned selector behavior.

## Final Policy

Governance should assume that any privileged transaction can permanently change protocol integrity.

That means every signer should review actions as if they are signing custody movement, because operationally they are.
