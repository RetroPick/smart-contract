# RetroPick V1 Governance and Change-Control Policy

## Purpose

This document defines how privileged control of RetroPick V1 must be exercised in production.

It covers:

- governance scope
- Safe ownership model
- change categories
- approval thresholds
- emergency vs non-emergency actions
- required artifacts before privileged changes
- post-change validation and rollback expectations

## Governance Scope

Governance controls the following privileged actions:

- UUPS upgrades
- module code-hash allowlisting
- module registration and revocation
- selector routing changes
- oracle adapter replacement
- oracle cursor reset
- yield-router replacement
- yield-router failure-state reset
- pause and unpause
- emergency recovery actions
- treasury change
- worker change
- deposit executor change
- trusted reporter rotation and correction ownership actions

These powers are equivalent to protocol-level custody and settlement control.

## Governance Structure

### Admin Safe

All protocol governance must be executed through the Admin Safe.

Requirements:

- no EOA admin in production
- hardware-wallet signers only
- written owner roster
- written threshold policy
- signer rotation procedure

Recommended threshold:

- guarded pilot: `2-of-3` acceptable temporarily
- real production: `3-of-5`
- higher TVL: `4-of-7` if operationally sustainable

### Treasury Safe

Treasury custody must be separated from Admin Safe where possible.

This reduces the blast radius of:

- operational compromise
- signer compromise
- governance abuse

### Reviewer Roles

At minimum, every privileged change must involve:

- one change owner
- one independent technical reviewer
- one governance approver through Safe threshold

High-risk changes require:

- two independent reviewers
- written rollback plan

## Change Classification

### Class A: Emergency Actions

Includes:

- pause
- trusted reporter emergency rotation
- yield emergency withdraw
- routed-principal recovery operations

Requirements:

- fastest Safe path permitted by signer policy
- no timelock if immediate action is required
- incident ticket must still be created
- post-incident review is mandatory

### Class B: High-Risk Planned Actions

Includes:

- upgrade
- module allowlist or registration
- selector rewiring
- router replacement
- oracle replacement
- rolling lifecycle reset

Requirements:

- written change request
- dry-run evidence
- two technical reviewers
- explicit post-change checklist
- scheduled maintenance window

### Class C: Medium-Risk Planned Actions

Includes:

- worker change
- treasury change
- deposit executor updates
- oracle cursor reset
- failure-state reset
- trusted-reporter clear operations

Requirements:

- written change request
- one technical reviewer
- decoded Safe transaction review

### Class D: Routine Financial Actions

Includes:

- fee withdrawals

Requirements:

- accounting review
- treasury reviewer signoff
- Safe threshold approval if treasury path requires it

## Required Artifacts Before High-Risk Changes

Before any Class B action, governance must have:

1. change ticket
2. reason for change
3. exact calldata or script reference
4. expected state changes
5. dry-run output
6. affected contracts and templates
7. rollback or containment plan
8. signer approvals

## Upgrade Policy

Upgrades are never routine.

Required before upgrade:

- full test pass
- dry-run of [script/production/UpgradeProduction.s.sol](/home/asyam/dev/Project/RetroPick/V1/contract/script/production/UpgradeProduction.s.sol:1)
- storage-layout validation via OpenZeppelin upgrades tooling
- implementation diff review
- post-upgrade validation checklist

Mandatory governance rule:

- protocol must be paused before production upgrade unless there is a documented exception approved by all reviewers

## Module Governance Policy

Module governance is one of the highest-risk surfaces in the system.

Before allowlisting or registering a module:

1. verify source commit
2. reproduce bytecode
3. compute code hash
4. confirm storage-layout expectations
5. confirm module is intended to inherit `MarketEngineState`-compatible layout
6. review selector manifest
7. confirm no unintended selectors are introduced

Never approve a module based only on:

- a local binary
- an unreviewed branch
- a verbal signoff

## Oracle Governance Policy

Before changing any oracle adapter:

1. identify affected template set
2. confirm change requires pause if replacing a non-zero adapter
3. evaluate active-epoch implications
4. decide whether cursor reset is required
5. document expected settlement-source behavior after the change

Governance must never authorize:

- broad cursor resets without template/feed scoping
- mid-incident oracle changes without written rationale

## Yield Router Governance Policy

Before router replacement:

1. confirm `totalRoutedPrincipal == 0`
2. confirm new router bytecode and deployment record
3. confirm emergency unwind assumptions
4. confirm intended `yieldFeeBps`
5. plan maintenance window under pause

Governance must never authorize:

- replacing a router while outstanding routed principal exists
- enabling an unreviewed router under production capital

## Pause / Unpause Governance Policy

Pause may be triggered for:

- router failure
- oracle integrity uncertainty
- settlement uncertainty
- governance-key compromise
- module or upgrade suspicion

Unpause requires:

- incident commander recommendation
- technical reviewer signoff
- no unresolved recovery state
- no disabled router state if production routing is expected
- Safe approval

## Trusted Reporter Governance Policy

If trusted-reporter markets are active, governance must define:

- reporter key custody
- max signature age policy
- correction approval path
- compromise response path
- reporter rotation approval requirements

Reporter rotation is a high-risk governance action and must be treated as such.

## Recordkeeping

Governance must maintain:

- owner roster
- threshold policy
- privileged transaction log
- upgrade history
- module allowlist history
- router/oracle change history
- incident log

## Final Policy Statement

For RetroPick V1, governance is not a cosmetic layer.

Governance is part of the protocol’s security boundary.

Any team operating this system without disciplined Safe governance, change review, and written change records is operating outside the intended safety model.
