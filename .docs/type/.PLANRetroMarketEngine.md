# RetroPick Persistent Vault Market Engine

## Re-architected protocol docs

## 0. Executive summary

RetroPick should not be modeled as “a fresh pot every round” if the goal is to reduce account creation and let users rebalance within the same live market. Instead, the protocol should be modeled as:

* one **market template**
* one **persistent ActiveVault**
* one **persistent ClaimsVault**
* one **persistent FeeVault**
* repeated **epoch ledgers**
* repeated **user position ledgers per epoch**

The vaults are persistent, but the **economic accounting is epoch-isolated**.

That means:

* **custody is shared**
* **liabilities are not shared**
* **winner determination is per epoch**
* **claims are per epoch**
* **fees are segregated**
* **users may rebalance before lock**
* **no unresolved liabilities are rolled into free trading capital**

Solana PDAs are a good fit for this because they are deterministically derived from seeds, have no private key, and the program can sign for them through `invoke_signed`. Anchor’s PDA constraints let the program enforce correct addresses at the instruction boundary. ([Solana][1])

---

# 1. The new key abstraction

You should no longer think in terms of:

* one new pool per round
* one vault per round
* “reset pool to zero and start again”

You should think in terms of:

### 1. Market metadata

What market this is:

* BTC 5m Direction
* ETH 1h Threshold
* SOL Daily Range Close

### 2. Persistent custody

Where the real tokens live:

* `ActiveVault`
* `ClaimsVault`
* `FeeVault`

### 3. Epoch accounting

Which liabilities belong to which time slice:

* epoch 1001
* epoch 1002
* epoch 1003

### 4. Resolution logic

How oracle data maps to the winning outcome

### 5. Payout logic

How losing exposure is redistributed to winners after fees

This is the correct abstraction because **market type changes resolution logic**, while **custody, epoch accounting, switching, fee segregation, and claim logic can stay shared**.

---

# 2. Core design thesis

The right architecture is:

## One market, persistent vaults, rolling epochs

For example, for **BTC up/down every 5 minutes**:

* one market template: `BTC_5M_DIRECTION`
* one persistent `ActiveVault`
* one persistent `ClaimsVault`
* one persistent `FeeVault`
* repeated epoch ledgers:

  * `epoch_1001`
  * `epoch_1002`
  * `epoch_1003`

Each epoch stores:

* open time
* lock time
* resolve time
* lock price
* final price
* total YES exposure
* total NO exposure
* switch fees accrued
* settlement fees accrued
* total claim liability
* winner side
* total claimed

The vaults persist. The accounting resets per epoch.
That is the safe way to “reuse the same pool.”

# 3. What changed from the old docs

The old model assumed:

* a market instance is the main custody boundary
* each round has a vault or isolated pool
* payout engine is attached directly to that market instance

The new model changes that to:

## Old mental model

`Market(epoch)` owns its own pot

## New mental model

`MarketTemplate` owns persistent vaults, while each `Epoch` owns isolated accounting

That means the protocol is no longer:

> one vault per market instance

It becomes:

> one persistent market custody domain with per-epoch liability segregation

This is the crucial re-architecture.

# 4. The right architecture

## A. Market Definition Layer

Defines:

* asset
* cadence
* outcome model
* resolution rule
* oracle feed
* fee policy
* min/max stake
* switchability rules

Examples:

### Direction

* BTC up or down in 5m
* outcomes: `YES`, `NO`
* rule: `final_price > lock_price => YES`, else `NO`

### Threshold

* BTC above 120k by 23:59 UTC
* outcomes: `YES`, `NO`
* rule: `final_price >= threshold => YES`

### Range-close

* ETH closes in a defined band
* outcomes: `RANGE_1`, `RANGE_2`, `RANGE_3`, ...
* rule: select the interval containing final price

This layer is market metadata only.

---

## B. Persistent Custody Layer

Defines the vault architecture.

### `ActiveVault`

Holds current live collateral for open trading and locked-but-unresolved epochs.

### `ClaimsVault`

Holds resolved but unpaid winner liabilities.

### `FeeVault`

Holds protocol fees that are safe to withdraw.

This is the major innovation.

Instead of many per-epoch vaults, the protocol reuses a persistent custody domain and moves balances between vault roles only when economically necessary.

Because PDA accounts are deterministic and program-signable through runtime mechanisms, this pattern fits Solana well. ([Solana][1])

---

## C. Epoch Accounting Layer

Defines:

* one ledger per recurring time window
* one set of outcome totals per epoch
* one claim liability per epoch
* one winner per epoch
* one settlement result per epoch

Epochs are the true settlement boundary.

This is what prevents insolvency when vault custody is shared.

---

## D. Resolution Layer

Defines:

* how oracle data becomes a winning outcome

The backend may fetch and pass oracle update accounts or payloads, but the program should validate the oracle input and compute the winner onchain. Pyth’s Solana integration explicitly supports passing price update accounts into the instruction that needs the price. Switchboard’s current Solana tutorial similarly uses a managed oracle flow and then has the program read the canonical oracle account in the same transaction. ([docs.pyth.network][2])

---

## E. Payout Layer

Defines:

* claim liability creation
* winner payout formula
* fee segregation
* claim withdrawal
* cancellation/refund path

This layer remains generic across market types.

# 5. The new economic model

## One real vault does not mean one undifferentiated pool

The vaults hold tokens physically.

Program state holds economic meaning.

For a binary market:

* tokens sit in `ActiveVault`
* epoch state stores:

  * `yes_total`
  * `no_total`

So the vault does **not** need:

* `YesVault`
* `NoVault`

Instead:

* vault = custody
* yes/no = state ledger

Example:

* `ActiveVault` balance = 1,000 USDC
* epoch ledger:

  * `yes_total = 600`
  * `no_total = 400`

That means YES and NO are accounting buckets, not separate token accounts.

This is the cleanest design because side switching becomes a ledger update, not a token transfer between vaults.

# 6. Why this is not PancakeSwap Prediction

Pancake-style prediction is closer to:

* isolated round pools
* one fixed entry side per round
* round closes
* winners claim from that round’s pot
* next round is fresh

This design is different:

* custody is persistent
* epochs are rolling ledgers
* users can rebalance before lock
* claims are reserved into a shared claims vault
* fees are segregated into a shared fee vault

So the product can still feel similar at the UX layer, but the protocol architecture is different.

The correct description is:

> **persistent-vault rolling parimutuel epochs with pre-lock side rebalancing**

# 7. Generalized payout engine under the new architecture

The old formula still mostly works, but the accounting boundary changes from “market instance” to “epoch ledger.”

## Core concepts

Each epoch has:

* `outcome_count`
* `pool[outcome_id]`
* `winning_outcome_mask`
* `status`
* `claim_liability_total`
* `claimed_total`
* `settlement_fee_total`

Each user position has:

* `stake[outcome_id]`
* `fees_paid`
* `claimed`

Then:

```text
total_pool = Σ pool[i]
winning_pool = Σ pool[winners]
losing_pool = total_pool - winning_pool
fee = fee_policy(losing_pool or total_pool)
distributable_losing_pool = losing_pool - fee
```

User payout for a winner is:

```text
user_payout =
user_winning_stake +
(user_winning_stake / total_winning_pool) * distributable_losing_pool
```

This remains valid for:

* Direction
* Threshold
* Range-close
* multi-outcome discrete markets

The important change is:

* payout liability is moved into `ClaimsVault`
* not kept implicitly inside the active trading pot

# 12. Lifecycle under the new design

## A. Create template

Admin creates a recurring template:

* asset
* cadence
* resolver type
* oracle feed
* fee rules
* switching rules

## B. Create persistent vaults

At template initialization:

* create `ActiveVault`
* create `ClaimsVault`
* create `FeeVault`

This happens once, not per epoch.

## C. Open epoch

Worker creates next `Epoch` ledger:

* times set
* pools zeroed
* status = `Open`

No new vault created.

## D. Place position

User deposits to a side:

* transfer tokens into `ActiveVault`
* increase `epoch.pool[outcome]`
* increase `position.stake[outcome]`
* update ledger totals

## E. Switch side

Before lock, user may switch:

* debit source outcome
* apply switch fee
* credit destination outcome with net amount
* increase fee reserve or accrued fee bucket
* no inter-vault token movement required

## F. Lock epoch

At `lock_at`:

* stop deposits and switching
* store lock checkpoint if required by resolver

## G. Resolve epoch

At `resolve_at`:

* backend submits oracle data/accounts
* program validates oracle data
* program computes winner onchain
* program computes fee
* program computes total claim liability
* program moves aggregate payable amount from `ActiveVault` to `ClaimsVault`
* program moves settled protocol fees to `FeeVault`
* epoch status = `Resolved`

## H. Claim

Winner claims:

* compute payout from epoch position
* transfer from `ClaimsVault`
* update `claimed_total`
* mark position claimed or increment claimed amount

## I. Advance

Worker opens next epoch using the same vault set.

That is the final recurring model.

# 13. New switching model

## What switching means

Switching means:

> while epoch is open, the user may reduce exposure on one outcome and increase exposure on another, paying a switch fee.

It does **not** mean:

* changing the market question
* changing oracle inputs
* changing epoch timestamps
* changing the settlement rule
* moving funds across epochs

So switching is a position reallocation, not a market mutation.

---

## Binary example

Before:

* `yes_total = 1000`
* `no_total = 800`
* Alice: `yes = 100`, `no = 0`

Alice switches 40 from YES to NO, fee 2%.

After:

* Alice `yes = 60`
* Alice `no = 39.2`
* `yes_total = 960`
* `no_total = 839.2`
* `switch_fee_total += 0.8`

No token transfer between YES and NO vaults is needed, because there are no YES/NO vaults. It is one custody vault plus internal ledgers.

---

## Multi-outcome example

For range-close:

* `RANGE_1`
* `RANGE_2`
* `RANGE_3`
* `RANGE_4`

Switching generalizes to:

* debit `stake[from_outcome]`
* credit `stake[to_outcome] - fee`
* update `pool[from_outcome]`
* update `pool[to_outcome]`

So the model still works for multi-outcome discrete markets.

# 14. Resolution model

The settlement engine should ask only one question:

> which outcome IDs won for this epoch?

Each resolver outputs:

* `winning_outcome_mask`
  or
* `winning_outcome_ids`

Examples:

### Direction

* YES = price up
* NO = price down or not up, depending on rule

### Threshold

* YES = final >= threshold
* NO = otherwise

### Range-close

* one winning range

The backend should never be trusted to submit only “winner = YES.”
The backend should submit oracle data/accounts, and the contract should validate and compute the winner onchain. Pyth documents this as passing price update accounts into instructions that need price data. Switchboard documents a managed update system where the program reads the canonical oracle account after verification/storage instructions in the same transaction. ([docs.pyth.network][2])

---

# 15. Claims reserve model

## Why a shared ClaimsVault is better

Instead of:

* one reserve vault per user
* or keeping resolved liabilities mixed forever in ActiveVault

use:

* one `ClaimsVault` per market template

At resolve:

* compute total payable amount to winners
* transfer aggregate claim liability from `ActiveVault` to `ClaimsVault`

This gives you:

* ring-fenced winner liabilities
* easier treasury safety
* cleaner balance-sheet reasoning
* no per-user vault explosion

This is safer than “resetting the pool to zero + fee buffer.”

---

## Why not one reserve vault per user

Because that would:

* create too many token accounts
* increase rent overhead
* increase instruction complexity
* make batch resolution fragile
* make every epoch operationally heavier

The correct split is:

* aggregate claims in one vault
* user entitlements in position state

---

# 16. Fee model

You now have three relevant fee types.

## A. Entry fee optional

Taken when entering a side.

## B. Switch fee

Taken when moving from one side to another before lock.

## C. Settlement fee

Taken from losing pool or total pool at resolution, depending on policy

Recommended V1 policy:

* keep switch fee explicit
* keep settlement fee explicit
* define exactly whether settlement fee is applied to total pool or losing pool
* move withdrawable fees into `FeeVault`

Do not let treasury withdraw from:

* `ActiveVault` reserved collateral
* `ClaimsVault`

Treasury should withdraw only from `FeeVault`.

# 20. Solvency invariants

These are mandatory.

## Invariant 1

For an open or locked epoch:

`sum(position.stake[outcome]) across all users == epoch.pool[outcome]`

for each outcome.

## Invariant 2

On switch:

`gross_debit = net_credit + switch_fee`

## Invariant 3

After lock:

* no deposits
* no switching
* no position mutation

## Invariant 4

For resolved epoch:

`claimed_total <= claim_liability_total`

## Invariant 5

Market-level solvency:

`active_collateral + claims_reserve + withdrawable_fee_reserve + insurance_reserve <= total vault balances`

## Invariant 6

Treasury withdrawals must only reduce `FeeVault`

## Invariant 7

ClaimsVault obligations from prior epochs must never be counted as available liquidity for new trading

These invariants are the backbone of the persistent-vault design.

# 21. Main attack surfaces

## A. Lock-boundary race

User tries to switch or deposit exactly at lock.

Mitigation:

* hard onchain time/slot cutoff

## B. Double claim

User claims twice.

Mitigation:

* `claimed` flag or claimed amount in `Position`

## C. Liability leakage

Old winner liabilities used as current trading liquidity.

Mitigation:

* move aggregate claim liability to `ClaimsVault`
* strict reserve accounting

## D. Premature treasury withdrawal

Treasury drains fees before liabilities are reconciled.

Mitigation:

* segregated `FeeVault`
* treasury can only withdraw from it

## E. Incorrect switch accounting

Pool totals and position totals diverge.

Mitigation:

* shared internal helper functions
* invariant tests
* property-based fuzzing

## F. Stale oracle data

Bad checkpoint leads to bad winner.

Mitigation:

* freshness checks
* publish-time validation
* void path if stale or invalid

## G. Wrong PDA passed

Malicious or mistaken accounts passed into instruction.

Mitigation:

* Anchor `seeds` and `bump` constraints on all critical accounts. Anchor documents these constraints as security checks for correct PDA derivation. ([Anchor Language][3])

# 25. Cost and account implications

This architecture reduces repeated vault creation cost because:

* vaults are created once per market template
* epochs are lightweight state accounts
* positions are per-user per-epoch accounts
* no new vault per epoch

Transaction fees on Solana still apply per transaction, with a base fee charged per signature and optional prioritization fees, but you avoid the repeated account-creation pattern of new vaults every cycle. ([Solana][5])

The true scaling cost is now mostly:

* position account growth
* epoch account growth
* worker / RPC usage
* oracle update txs

not vault churn.

---

# 26. Storage guidance

If some aggregate state becomes large, Anchor’s zero-copy path exists via `AccountLoader`, and Anchor documents that the normal `init` path is limited to about 10,240 bytes due to CPI allocation limits. Larger accounts require a different initialization path using `zero`. ([Anchor Language][6])

For V1, avoid needing large accounts by:

* keeping epoch accounts compact
* one position per user per epoch
* storing only aggregate outcome totals on epoch
* avoiding unbounded vectors
