# RetroPick V1 Module Release Checklist

## Purpose

This document defines the release process for any MarketEngine delegatecall module.

It exists because the module system is a privileged risk surface:

- module bytecode is delegatecalled against proxy storage
- storage corruption is possible if the wrong module is approved
- selector routing can change live behavior without changing the proxy address

## Scope

This applies to:

- new modules
- modified modules
- module re-registration
- selector remaps to existing modules

## Release Philosophy

The on-chain checks are necessary but not sufficient.

The dispatcher checks:

- allowed code hash
- registered module code hash
- storage-compatibility marker

Those checks do not prove full storage-layout safety.

The real safety standard is:

- reviewed source
- reproducible build
- expected bytecode hash
- explicit selector manifest
- governance approval

## Mandatory Release Artifacts

Every module release must produce:

1. source commit hash
2. compiler / Foundry version
3. module file path
4. deployed module address
5. expected code hash
6. selector manifest
7. reviewer signoff
8. deployment and registration transaction hashes

## Pre-Release Review

Before approving module bytecode:

1. identify whether this is a new module or modified module
2. review source diff
3. confirm intended selectors
4. confirm intended storage assumptions
5. confirm the module is compatible with `MarketEngineState`
6. confirm no unexpected external call behavior was introduced
7. confirm no governance-sensitive behavior was changed silently

## Build Reproducibility

Before allowlisting a hash:

1. build module from the reviewed commit
2. record toolchain versions
3. compute bytecode hash
4. compare against the proposed production hash

No module hash may be approved if:

- it cannot be reproduced
- it was produced from an unreviewed commit
- the artifact source is unknown

## Selector Manifest

Every release must include a selector manifest containing:

- selector hex value
- function signature
- intended module address
- whether selector should be immutable
- previous module address if being changed
- reason for change

No selector routing should be performed without this manifest.

## Release Steps

### 1. Internal Approval

Collect:

- technical reviewer signoff
- governance reviewer signoff
- release owner signoff

### 2. Pause Decision

Default policy:

- pause before module registration or selector rewiring in production

If governance chooses not to pause, that exception must be documented explicitly.

### 3. Allowlist Code Hash

Through Admin Safe:

- call `allowModuleCodeHash(codeHash)`

Validate:

- emitted `ModuleCodeHashAllowed`
- code hash matches release artifact

### 4. Register Module

Through Admin Safe:

- call `registerModule(module, expectedCodeHash)`

Validate:

- emitted `ModuleRegistered`
- module address matches release record
- code hash stored matches expected

### 5. Route Selectors

Through Admin Safe:

- call `setSelectorModule(selector, module, makeImmutable)` for each selector

Validate:

- emitted `SelectorModuleSet`
- selector now resolves to intended module

### 6. Post-Release Checks

Verify:

- no unexpected selectors changed
- read paths still work
- key user flows still work
- config values unchanged
- no unexpected module was approved or registered

## Rollback Policy

Every module release must include a rollback plan.

Possible rollback tools:

- `revokeModule`
- selector remap back to prior approved module
- full pause
- upgrade path if issue is systemic

Rollback must be prepared before release, not invented during the incident.

## Red Flags

Do not release if any of the following is true:

- module source was not independently reviewed
- bytecode cannot be reproduced
- selectors are not fully enumerated
- reviewer cannot explain storage assumptions
- release is bundled with unrelated router/oracle/upgrade changes
- Safe signers are asked to sign opaque calldata without decoded review

## Minimal Production Signoff Standard

For any production module release:

- two reviewers minimum
- release manifest archived
- code hash archived
- selector manifest archived
- Safe tx hashes archived
- post-change checks completed

## Final Policy Statement

The module system is powerful enough to compromise the protocol if run carelessly.

For that reason, module release discipline is not optional engineering overhead.

It is a core production security control.
