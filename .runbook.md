# RetroPick V1 Operator Runbook

## Purpose

This runbook defines how operators should run the deployed RetroPick V1 MarketEngine in production.

This protocol is intentionally centralized. Operational safety is part of protocol safety.

The runbook covers:

- roles and responsibilities
- normal operating procedures
- change-management procedures
- incident response
- yield-router recovery procedures
- oracle and trusted-reporter procedures
- rolling-market recovery procedures
- launch and post-change validation

## Security Model

The engine is not trustless. The following powers are privileged and security-critical:

- UUPS upgrades via dispatcher admin
- module code-hash allowlisting and module registration
- selector routing to delegatecall modules
- yield-router replacement and reset
- oracle replacement
- pause and unpause
- emergency recovery and recovered-balance reassignment
- treasury fee withdrawal
- trusted-reporter rotation and clear operations for reporter-settled markets

Operators must treat these powers as equivalent to custody over user funds and settlement integrity.

## Roles

### 1. Governance / Admin Multisig

Owns all privileged MarketEngine and TrustedReporter admin actions.

Permitted actions:

- pause and unpause
- set worker authority
- set treasury
- set deposit executor
- set yield router and yield fee
- set oracle adapters
- reset oracle cursor
- emergency yield withdrawal
- reconcile routed principal
- reassign recovered balance
- finalize recovered yield
- reset yield-router failure state
- initialize markets
- withdraw fees
- allow module code hash
- disallow module code hash
- register module
- revoke module
- set selector module
- upgrade dispatcher implementation
- trusted reporter rotation and correction actions

Requirements:

- must be a multisig, never an EOA
- minimum signer threshold should be documented and enforced
- emergency and non-emergency signer policies must be distinct
- no signer should execute privileged changes from a hot browser wallet on an unmanaged device

### 2. Worker Authority

Used for operational epoch lifecycle actions and reward claims.

Permitted actions:

- lock and resolve manual epochs where worker auth is allowed
- batch lifecycle operations where configured
- keeper LM reward claim operations

Requirements:

- worker key should be replaceable by admin immediately
- worker key should not have upgrade, module, treasury, router, or oracle authority
- worker should run from dedicated infrastructure with alerting

### 3. Treasury Operator

Responsible for treasury receipt monitoring and fee accounting.

Permitted actions:

- observe fee accrual and treasury flows
- optionally initiate fee withdrawals if treasury is authorized directly

Requirements:

- treasury destination must be a controlled multisig or institutional custody wallet
- treasury address changes require full governance review

### 4. Oracle Operations

Responsible for:

- oracle adapter health
- feed configuration correctness
- trusted-reporter key custody and correction procedures

### 5. Incident Commander

Single accountable human for live incidents.

Responsibilities:

- decide whether to pause
- coordinate multisig signers
- approve recovery sequence
- maintain incident log
- sign off on unpause readiness

## Operational Principles

### 1. Default to fail closed

When operator confidence is low:

- pause first
- preserve evidence
- stop routing new funds
- do not “try random fixes” on live state

### 2. No ad hoc privileged changes

Do not perform live privileged actions without:

- a written reason
- expected state transition
- post-change validation checklist
- rollback plan where applicable

### 3. Never combine unrelated changes

Do not combine, in one maintenance window:

- oracle replacement
- router replacement
- module registration
- selector rewiring
- upgrade

Each should be its own controlled change unless the runbook explicitly requires a paired operation.

### 4. Pause before risky state surgery

The code already enforces pause for several sensitive operations, but operators must also adopt pause as a governance rule for any high-risk intervention.

## Daily Operating Checklist

At least once per day, and before each active market window:

1. Confirm `admin`, `treasury`, and `workerAuthority` are the expected addresses.
2. Confirm the configured yield router matches the approved deployment artifact.
3. Confirm yield router is not disabled unless incident handling is active.
4. Confirm all active oracle adapter addresses match the approved configuration matrix.
5. Confirm there is no unexpected non-zero `totalUnreconciledRecovered`.
6. Confirm there is no unexpected rolling halt.
7. Confirm no unauthorized module, selector, or upgrade event occurred.
8. Confirm trusted-reporter key and max signature age are unchanged unless an approved maintenance action is in progress.

## Pre-Launch Checklist For A New Environment

Before enabling deposits in a new deployment:

1. Verify the deployed dispatcher implementation and proxy addresses.
2. Verify initialization parameters:
   - stake token
   - base oracle
   - admin
   - treasury
   - worker
   - default settlement fee
   - max switch fee
   - max outcomes
   - oracle config
3. Verify approved module code hashes match the intended artifacts.
4. Verify registered module addresses match audited bytecode.
5. Verify selector routing is complete and matches the approved deployment manifest.
6. Verify treasury and worker addresses by independent out-of-band review.
7. Verify supported market templates are initialized and parameter-reviewed.
8. Verify monitoring is live before first deposit is accepted.

## Normal Operations

### Opening and Running Manual Epochs

Standard flow:

1. Admin ensures template is initialized.
2. Worker opens epoch with reviewed timestamps.
3. Users deposit and optionally switch side.
4. Worker locks epoch after lock time and oracle conditions are satisfied.
5. Worker resolves epoch after resolve time and oracle conditions are satisfied.
6. Users claim.
7. Treasury withdraws fees only after independent accounting review.

Operator rules:

- never open epochs with timings outside the approved template envelope
- never resolve early to “catch up”
- if oracle quality is in doubt, pause and investigate rather than forcing lifecycle progression

### Running Rolling Markets

Standard flow:

1. Confirm rolling template is initialized and in the expected phase.
2. Monitor automatic/worker-driven rolling progression.
3. If `RollingHalted` emits, enter incident mode immediately.

Operator rules:

- do not reset rolling lifecycle for convenience
- do not continue user acquisition or promotion for a halted rolling market until the incident is closed

## Change Management

### 1. Yield Router Change Procedure

Function:

- `setYieldRouter(address router, uint16 feeBps)`

Hard preconditions from code and governance:

- must be admin
- replacement should be performed under pause
- old router cannot be replaced while `totalRoutedPrincipal != 0`, unless it is the same router

Procedure:

1. Announce maintenance window internally.
2. Pause protocol.
3. Confirm `totalRoutedPrincipal == 0`.
4. Verify new router deployment address and bytecode.
5. Verify fee basis points are approved.
6. Execute router change.
7. Confirm `YieldRouterSet` emitted expected old/new addresses and fee.
8. Confirm failure counters reset only if expected.
9. Unpause only after post-change checks pass.

Post-change checks:

- router address matches intended address
- fee bps matches intended value
- deposits route as expected in staging or rehearsal environment before public use

### 2. Oracle Adapter Change Procedure

Functions:

- `setRateOracle`
- `setSmartDataOracle`
- `setMacroOracle`
- `setEquityOracle`
- optionally `resetOracleCursor`

Hard preconditions:

- replacing a non-zero oracle with a different address requires pause
- `resetOracleCursor` is forbidden if active epoch status is `Open` or `Locked`

Procedure:

1. Pause protocol.
2. Identify every template affected by the oracle change.
3. Confirm no affected template has an active epoch in `Open` or `Locked` state if cursor reset is needed.
4. Execute oracle replacement.
5. Reset cursors only for affected templates/feeds that need continuity reset.
6. Review oracle snapshot implications for already-open epochs.
7. Unpause only after validation of settlement-source expectations.

Do not:

- change oracle adapters mid-incident unless that change is part of the approved incident plan
- reset cursors broadly “just in case”

### 3. Module Registration / Selector Routing Procedure

Functions:

- `allowModuleCodeHash`
- `registerModule`
- `setSelectorModule`
- `revokeModule`
- upgrades via UUPS

This is the highest-risk governance surface in the system.

Mandatory controls:

- multisig only
- two-person artifact verification minimum
- bytecode hash comparison against approved build output
- storage-layout review against `MarketEngineState`
- written selector-routing manifest

Procedure:

1. Freeze non-emergency changes.
2. Pause protocol unless the change is provably non-stateful and low risk.
3. Verify module artifact:
   - source commit
   - compiler version
   - build reproducibility
   - code hash
   - storage compatibility inheritance
4. Allow module code hash.
5. Register module.
6. Set selector routes one by one against the signed manifest.
7. Validate every changed selector.
8. Resume only after post-change smoke checks.

Never:

- allowlist a hash that has not been independently reproduced
- register a module directly from an unreviewed local build
- set selector routes without a manifest

### 4. Upgrade Procedure

Dispatcher is UUPS-upgradeable. Treat upgrades as equivalent to system replacement.

Required controls:

- full pause
- full signer review
- release notes
- storage layout review
- rollback plan
- post-upgrade validation on a fork or staging environment first

Minimum post-upgrade checks:

- proxy still points to expected implementation
- core selector routes still resolve correctly
- config values unchanged
- deposits, claims, and read paths work
- module approval registry unchanged unless intentionally modified

## Incident Response

### Incident Severity Levels

`sev0`

- active or suspected loss of funds
- settlement corruption
- malicious module or upgrade
- compromised admin or trusted-reporter key

`sev1`

- router disabled
- emergency recovery required
- rolling lifecycle halted
- oracle source failure affecting settlement

`sev2`

- worker outage
- monitoring outage
- correction event required for trusted-reporter market

### Universal Incident Procedure

1. Record incident start time and trigger.
2. Freeze unrelated changes.
3. Decide whether to pause immediately.
4. Identify impacted templates and epochs.
5. Preserve event and state evidence.
6. Use the template-specific recovery flow below.
7. Do not unpause until:
   - state is understood
   - balances are reconciled
   - pending recovery is zero or intentionally accounted for
   - incident commander signs off

## Yield Router Incident Runbook

Triggers:

- `YieldRouterFailureRecorded`
- `YieldRouterDisabled`
- manual evidence of router insolvency, malfunction, or withdrawal failure

Immediate actions:

1. Pause protocol.
2. Identify affected templates and epochs with routed principal.
3. Stop all non-essential lifecycle actions.
4. Determine whether router is temporarily failing or structurally compromised.

Recovery sequence:

1. Execute `yieldEmergencyWithdraw(templateId)` for each affected template that can be unwound.
2. Confirm `YieldEmergencyWithdrawn` emitted expected gross amount.
3. For each affected epoch, execute `reconcileEpochRoutedPrincipal(templateId, epochId, recoveredPrincipal)` only up to actual recovered amount.
4. If balance was returned to the wrong template bucket, use `reassignRecoveredBalance(fromTemplateId, toTemplateId, amount)`.
5. When and only when `totalRoutedPrincipal == 0`, execute `finalizeRecoveredYield(templateId)` if excess recovered yield remains.
6. If router disablement was incidental and resolved, reset failure state with `resetYieldRouterFailures()` while still paused.
7. Unpause only after:
   - `totalUnreconciledRecovered == 0`
   - no template has unresolved recovery debt that should block operations
   - incident commander signs off

Critical operator rules:

- never reconcile more than actually recovered
- never finalize recovered yield while any routed principal remains globally outstanding
- never unpause while `yieldRouterDisabled == true` or `totalUnreconciledRecovered != 0`

## Oracle Incident Runbook

Triggers:

- stale oracle data
- wrong adapter configuration
- continuity reset required
- feed integrity concern

Immediate actions:

1. Pause if active markets may settle incorrectly.
2. Determine which oracle class and templates are impacted.
3. Determine whether already-open epochs must continue under old snapshot semantics.

Recovery:

1. Replace oracle adapter only under pause.
2. Reset oracle cursor only for affected template/feed pairs and only if no active epoch is `Open` or `Locked`.
3. Revalidate settlement source for active and next epochs.
4. Resume only when worker and incident commander agree settlement inputs are sane.

## Trusted Reporter Incident Runbook

Triggers:

- reporter key compromise
- incorrect lock sample
- incorrect resolve result
- incorrect OHLC result
- stale signature replay concern

Immediate actions:

1. Pause the engine for all reporter-settled templates if settlement integrity is at risk.
2. Rotate reporter with `setTrustedReporter(newReporter)` if compromise or key loss is suspected.
3. Use the narrowest possible correction operation:
   - `clearLockSample`
   - `clearResolveResult`
   - `clearOhlcResult`

Rules:

- every clear must have an incident ticket and operator note
- every reporter rotation must be treated as a security event
- after a clear, repost only the corrected signed payload
- verify the emitted correction event

Important behavior:

- same-type replays are invalidated by nonces
- cross-type resolve/OHLC replays are also invalidated
- rotation increments `reporterEpoch`, invalidating pre-rotation signatures

## Rolling Market Halt / Reset Runbook

Triggers:

- `RollingHalted`
- repeated oracle failures
- recovery-pending block on rolling progression

Procedure:

1. Pause if the halt reason indicates broader system risk.
2. Identify:
   - halted active epoch
   - previous locked epoch
   - any routed principal or unreconciled recovery affecting the template
3. Resolve or recover the halted template state first.
4. Do not reset lifecycle until prerequisite halted and predecessor epochs are cleared.
5. If canceled while halted, ensure routed principal recovery requirements are satisfied before refund mode is finalized.
6. Use lifecycle reset only after the prior epoch chain is cleanly closed.

Never:

- reset rolling lifecycle to “unstick” the system before accounting is clean
- unpause while a rolling market is halted for unresolved financial reasons

## Unpause Readiness Checklist

Before any unpause:

1. `yieldRouterDisabled == false`
2. `totalUnreconciledRecovered == 0`
3. no unresolved emergency recovery workflow remains
4. no unreviewed module/selector/oracle/router changes remain pending
5. monitoring is live
6. incident commander and at least one additional reviewer sign off

## Post-Incident Review

For every `sev0` or `sev1` incident produce:

- timeline
- impacted templates and epochs
- actions taken
- on-chain transactions
- funds-at-risk assessment
- user impact assessment
- remediation items
- whether runbook updates are required

## Operational Anti-Patterns

Never do the following:

- use an EOA as admin in production
- route to a disabled router
- reconcile unrecovered principal
- finalize recovered yield before global routed principal is zero
- change modules from an unverified build
- rotate trusted reporter without documenting why
- clear reporter state without immediately checking emitted events and replacement payloads
- unpause because “the UI looks fine”

## Minimum Human Signoff Matrix

### Low-risk actions

- fee withdrawal
- worker rotation
- deposit executor updates

Required signoff:

- 1 operator request
- multisig threshold approval

### Medium-risk actions

- router failure-state reset
- oracle cursor reset
- trusted-reporter clear operation

Required signoff:

- 1 operator request
- 1 independent reviewer
- multisig threshold approval

### High-risk actions

- router replacement
- oracle replacement
- emergency recovery
- recovered-balance reassignment
- rolling lifecycle reset
- dispatcher upgrade
- module registration and selector rewiring
- trusted reporter rotation

Required signoff:

- incident or change ticket
- 2 independent reviewers
- multisig threshold approval
- post-change validation recorded

Update this runbook whenever any of the following change:

- oracle integration
- reporter model
- module architecture
- launch stage or governance policy

This runbook should be reviewed:

- before each public launch stage
- after every sev0 or sev1 incident
- after every upgrade that changes privileged behavior
