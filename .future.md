  # Plan: Exchange-Style View Layer for MarketEngine

  ## Summary

  Design the view layer as two separate read interfaces built on top of the existing engine state:

  - a Prediction Market view interface for frontends and traders
  - an Operator view interface for monitoring, recovery, and incident handling

  The recommended architecture is hybrid canonical:

  - the contract exposes canonical, current-state market/epoch/position snapshots on-chain
  - an off-chain indexer/operator service derives Polymarket-style historical percentage charts from events and current snapshots

  This is the right boundary because the current engine already stores enough data for rich current epoch views, but it does not store historical per-
  outcome price/probability time-series on-chain. Adding chart-history persistence to the contract would increase storage and lifecycle complexity and is
  not necessary for a production-grade view design.

  ## Key Changes

  ### 1. Replace the minimal view module with two explicit view surfaces

  Extend MarketEngineViewModule and IMarketEngine with grouped view functions for:

  - Prediction Market views
      - market/template summary
      - current epoch snapshot
      - user position snapshot
      - market pricing/probability snapshot per outcome
      - user claimability / settled-result snapshot
      - paginated user market activity helpers
  - Operator views
      - template health snapshot
      - router/recovery snapshot
      - rolling lifecycle snapshot
      - epoch accounting snapshot
      - oracle routing / oracle snapshot metadata
      - incident-state and paused-state helpers

  Keep the current raw getters (getEpoch, getVaultBalances, getRollingLifecycle, getUserEpochs) for backward compatibility, but treat them as low-level
  primitives. The new interfaces should be higher-level and frontend-friendly.

  ### 2. Add canonical on-chain structs for current-state snapshots

  Define compact read-only structs in IMarketEngine for the new view layer. The implementer should add these as explicit return types rather than returning
  many loose tuples.

  Recommended snapshot families:

  - MarketView
      - template metadata needed by UI
      - active epoch id
      - execution mode
      - whether market is paused / halted / claimable
      - oracle kind/class
      - outcome count
      - fee params relevant to UI
  - EpochView
      - epoch status and timing
      - total pool
      - per-outcome pools
      - winning mask
      - refund mode / claimable
      - routed principal
      - checkpoint/oracle summary needed by UI
      - total positions / liability / claimed totals
  - OutcomeView
      - outcome index
      - pool size
      - implied probability in 1e4 or 1e6 precision
      - display price on a 0-100% scale for UI compatibility
      - whether currently winning after settlement
  - PositionView
      - user stakes per outcome
      - total stake
      - claimed flag
      - claimed amount
      - pending claim estimate if epoch is claimable
      - winning stake / refundable amount if determinable from current epoch state
  - OperatorTemplateView
      - active / last resolved / halted epoch ids
      - rolling phase / halt reason
      - vault balances
      - total routed principal by template
      - unreconciled recovered amount
      - whether user ops should be blocked
      - whether protocol unpause is safe for that template
  - OperatorGlobalView
      - global paused state
      - current router address
      - router disabled flag
      - router failure count
      - total routed principal
      - total unreconciled recovered
      - treasury / worker / admin addresses

  ### 3. Define pricing semantics clearly for prediction-market UI

  For the PM view interface, the contract should expose canonical current implied percentages, but only for the current state of an epoch, not historical
  candles.

  Use this rule:

  - for an open or locked epoch, implied probability per outcome is derived from outcomePools[i] / totalPool
  - return the result as normalized percentages suitable for UI, e.g. scaled 0..1e6 or 0..10000
  - also expose the raw pool values so the frontend/indexer can choose its own rendering if needed

  Important implementation rule:

  - do not claim these are true orderbook prices
  - they are pool-implied market percentages from the AMM-style pooled stake distribution
  - for settled epochs, return settled winners/refund state rather than continuing to present them as live price quotes

  For multi-outcome markets, the sum of displayed percentages should equal the chosen fixed-point total except for bounded rounding drift.

  ### 4. Make position views exchange-like but current-state only

  Add a direct position getter. The engine currently has _positions storage but no public high-level position read path.

  The PM-facing position view should provide:

  - user’s stake on each outcome for (templateId, epochId)
  - total stake
  - total fees paid
  - claim state
  - estimated payout or refund if the epoch is claimable
  - zero or explicit “not claimable yet” when unresolved

  This should be enough for a frontend to render:

  - “my position”
  - “my average current directional exposure”
  - “claim now / already claimed / not settled”

  Do not attempt to reconstruct trade-by-trade fills or average entry price on-chain from current storage. That requires indexed event history and belongs
  off-chain.

  ### 5. Keep charting and level-history off-chain

  Polymarket-style charts require time-series points. The current contract emits enough events to support an external indexer, but it does not store
  historical probability snapshots.

  The plan should explicitly define the off-chain chart source:

  - source events:
      - PositionDeposited
      - SideSwitched
      - EpochOpened
      - EpochLocked
      - EpochResolved
      - EpochCancelled
      - rolling lifecycle events
  - optional enrichment:
      - periodic snapshot polling of new PM view getters
  - chart output:
      - per-outcome historical implied percentage series on 0-100% scale
      - current leaderboard / liquidity / volume summaries
      - operator analytics if desired

  This keeps the contract as the canonical source of current truth and the indexer as the source of historical presentation.

  ## Implementation Details

  ### Public interface shape

  Add new view functions in IMarketEngine and wire them through MarketEngineViewModule. The implementer should use a small number of high-signal methods
  instead of many tiny getters.

  Recommended methods:

  - getMarketView(bytes32 templateId) returns (MarketView memory)
  - getEpochView(bytes32 templateId, uint64 epochId) returns (EpochView memory)
  - getActiveEpochView(bytes32 templateId) returns (EpochView memory)
  - getOutcomeViews(bytes32 templateId, uint64 epochId) returns (OutcomeView[] memory)
  - getPositionView(bytes32 templateId, uint64 epochId, address user) returns (PositionView memory)
  - getOperatorTemplateView(bytes32 templateId) returns (OperatorTemplateView memory)
  - getOperatorGlobalView() returns (OperatorGlobalView memory)

  Optional but useful if the implementer can do it without bloating the interface:

  - getUserMarketViews(bytes32 templateId, address user, uint256 cursor, uint256 size)
      - wraps getUserEpochs plus lightweight epoch/position summaries for frontend pagination

  ### On-chain calculation rules

  Use only current canonical storage for on-chain views:

  - template metadata from _templates
  - lifecycle state from _ledgers
  - vault balances from _vaults
  - epoch state from _epochs
  - user position from _positions[positionKey(templateId, epochId)][user]
  - recovery state from _unreconciledRecoveredByTemplate, _templateRoutedPrincipal, totalRoutedPrincipal, totalUnreconciledRecovered

  For claim preview:

  - if epoch is not claimable, return zero preview and explicit status
  - if refundMode, preview refund from pos.totalStake
  - if resolved, use the same claim math path as claim logic, but in a read-only computation path

  For probability preview:

  - if totalPool == 0, return zeroed probabilities
  - otherwise compute each outcome’s implied percentage from outcomePools[i]
  - cap iteration to epoch.outcomeCount, never full fixed array length semantically

  ### Compatibility and safety

  - do not mutate storage
  - preserve existing raw getter behavior
  - keep all new functions in the view module only
  - maintain dispatcher selector wiring for the new view methods
  - avoid introducing any frontend-specific assumptions that would later be hard to change, such as candle interval policy or quote currency formatting

  ## Test Plan

  ### Contract tests

  Add tests for:

  - getMarketView
      - returns correct active epoch id, execution mode, halt status, and template metadata
  - getEpochView
      - reflects open, locked, resolved, voided, and canceled states correctly
  - getOutcomeViews
      - probabilities match pool ratios for 2-outcome and multi-outcome markets
      - zero-pool epoch returns zero percentages safely
      - settled epoch marks winning outcomes correctly
  - getPositionView
      - returns correct stakes, fees, and claim state
      - refund-mode preview works
      - resolved claim preview matches actual claim result before claiming
      - claimed position reflects claimed state after claim
  - getOperatorTemplateView
      - surfaces unreconciled recovery, routed principal, halted rolling state, and vault balances correctly
  - getOperatorGlobalView
      - reflects paused state, router state, and global recovery state correctly

  ### Scenario coverage

  Test at least these scenarios:

  - manual 2-outcome market with open -> lock -> resolve progression
  - multi-outcome market with live pool-derived probabilities
  - rolling market in healthy state
  - rolling market in halted state
  - router-disabled template with pending unreconciled recovery
  - resolved epoch in refund mode
  - resolved epoch with claimable winning position
  - user with no position
  - user with multi-side stakes where allowed

  ### Acceptance criteria

  The implementation is complete when:

  - frontend can render a current market card and current epoch odds without reading raw storage structs directly
  - frontend can render a user position panel for an epoch from one position getter
  - operator tooling can detect recovery, halt, paused, and router-disabled state from dedicated operator views
  - all new view math matches existing accounting behavior
  - no historical chart responsibility is pushed on-chain

  ## Assumptions

  - We are planning a hybrid design: current canonical state on-chain, historical charting off-chain.
  - We are planning separate PM and operator-facing interfaces, even if both live in the same Solidity module.
  - “Like Polymarket” means:
      - current displayed per-outcome percentages on a 0-100% scale
      - exchange-style current market/position views
      - not full on-chain historical chart persistence
  - We are not adding an orderbook abstraction. Prices are derived from pooled market state, not discrete bids/asks.
  - We are not planning trade-history reconstruction or average fill-price storage on-chain in this phase.

  # Plan: Prediction-Market + Operator View Interfaces with UI-Derived Payout X and On-Chain Yield Snapshots

  ## Summary

  Extend the view layer so the engine exposes rich current-state snapshots for both:

  - Prediction Market consumers: frontend/trader-facing views
  - Operators: monitoring, recovery, and risk-facing views

  The agreed design is:

  - historical charting stays off-chain
  - Kalshi-style Pays out x stays UI-derived
  - template yield data is exposed on-chain as a current snapshot, not as annualized APR/APY computed in-contract

  This means the contract becomes the canonical source for:

  - current epoch state
  - current per-outcome implied percentages
  - current user position state
  - current per-template yield state
  - current operator health/recovery state

  And the frontend/indexer derives:

  - Polymarket-style time-series charts
  - Kalshi-style Pays out x display from probabilities / pools
  - any annualized yield presentation

  ## Key Changes

  ### 1. Expand the view layer into two explicit surfaces

  Add grouped current-state view functions in IMarketEngine and implement them in MarketEngineViewModule:

  - Prediction Market views
      - current market/template snapshot
      - active epoch snapshot
      - per-outcome odds/probability snapshot
      - per-user position snapshot
      - claimability and payout-preview snapshot
      - current template yield snapshot visible to PM UI
  - Operator views
      - template health/recovery snapshot
      - global router/recovery snapshot
      - rolling lifecycle / halt snapshot
      - per-template oracle routing and current oracle metadata
      - vault/reserve/routed principal snapshot

  Keep existing low-level getters for compatibility:

  - getUserEpochs
  - getVaultBalances
  - getRollingLifecycle
  - getEpoch
  - unreconciledRecoveredByTemplate

  ### 2. Add canonical read structs in IMarketEngine

  Define explicit return structs so frontends and ops dashboards can consume stable typed snapshots instead of raw tuples.

  Recommended structs:

  - MarketView
      - template id / slug / asset symbol
      - market type / execution mode
      - outcome count
      - active flag
      - active epoch id
      - paused flag
      - rolling phase / halt reason if relevant
      - switch fee / settlement fee
      - whether yield routing is active for the template
  - EpochView
      - epoch id / status / cancel reason
      - timing
      - total pool
      - total positions
      - claimable / refund mode
      - routed principal
      - claim liability / refund liability / claimed total
      - checkpoint summary needed by UI
  - OutcomeView
      - outcome index
      - pool size
      - implied probability in fixed precision
      - display percentage basis for 0-100% chart/odds UI
      - winner flag after settlement
  - PositionView
      - user stakes per outcome
      - total stake
      - entry fees paid
      - switch fees paid
      - claimed flag
      - claimed amount
      - current pending claim or refund preview if claimable
  - TemplateYieldView
      - router assigned or not
      - router path if available
      - current principal
      - current routed value
      - unrealized yield amount = max(currentValue - principal, 0) for display
      - yield ratio = unrealizedYield / principal in fixed precision
      - yield fee bps context
      - flag if disabled router / recovery state means yield display is degraded
  - OperatorTemplateView
      - template routed principal
      - unreconciled recovered amount
      - vault active / claims / fees
      - active epoch id / last resolved epoch id
      - rolling phase / halt reason / halted epoch id
      - whether user ops are blocked by recovery
      - whether template is in unsafe state
  - OperatorGlobalView
      - global paused
      - router address
      - router disabled
      - failure count
      - total routed principal
      - total unreconciled recovered
      - admin / treasury / worker

  ### 3. PM-facing probability semantics

  For PM UI, expose current implied per-outcome probability directly from on-chain pool state:

  - for active epochs:
      - probability = outcomePools[i] / totalPool
  - return both:
      - raw pool values
      - normalized fixed-point probability values suitable for 0-100% UI rendering

  This is what the frontend/indexer should use for:

  - odds display
  - percentage chips
  - current market depth-like view
  - Polymarket-style line chart points

  Important rule:

  - these are pool-implied percentages
  - they are not an orderbook price
  - they are not promised as true fair odds
  - they are a live UI representation of current market state

  ### 4. Kalshi-style Pays out x stays off-chain, but contract exposes enough inputs

  The contract will not expose a dedicated payout multiplier field.

  Instead, the PM view will expose enough canonical inputs so the UI can derive it deterministically:

  - totalPool
  - outcomePools[i]
  - normalized probabilities
  - settlement fee basis points
  - epoch status / refund mode

  Frontend/indexer calculation policy:

  - derive displayed Pays out x from probability / pools
  - optionally show both:
      - gross implied multiple
      - net implied multiple after settlement-fee assumptions
  - this remains a UI convention, not a contract truth claim

  This avoids hard-coding one multiplier formula into the contract while still supporting Kalshi-style presentation.

  ### 5. Add per-template on-chain yield snapshot

  Expose current yield snapshot for every template that has a yield router assigned.

  Use existing router read surface:

  - currentValueOf(templateId)
  - principalOf(templateId)
  - scaledPrincipalOf(templateId)
  - stataSharesOf(templateId)
  - getTemplateYieldPath(templateId)

  Recommended on-chain semantics:

  - principal: template principal currently routed
  - currentValue: current underlying value reported by router
  - unrealizedYieldAmount: currentValue > principal ? currentValue - principal : 0
  - yieldRatio: unrealizedYieldAmount / principal in fixed precision if principal > 0 else 0

  Do not annualize in-contract.
  Do not promise APR/APY in-contract.
  Do not compute time-window-dependent yield rates on-chain.

  If the frontend wants:

  - APR
  - APY
  - “today yield”
  - rolling 7d yield

  those should be indexer/UI-derived from historical snapshots.

  ### 6. Add explicit degraded-state flags for yield display

  Template yield views should clearly signal when displayed yield data should be treated cautiously.

  Expose flags such as:

  - router configured or not
  - router disabled
  - unreconciled recovery pending
  - current routed principal zero or non-zero

  That lets the frontend/operator UI:

  - suppress misleading yield visuals during incidents
  - show degraded-state banners
  - distinguish healthy routed yield from recovery mode

  ## Implementation Details

  ### Public interface additions

  Add new IMarketEngine functions such as:

  - getMarketView(bytes32 templateId) returns (MarketView memory)
  - getActiveEpochView(bytes32 templateId) returns (EpochView memory)
  - getEpochView(bytes32 templateId, uint64 epochId) returns (EpochView memory)
  - getOutcomeViews(bytes32 templateId, uint64 epochId) returns (OutcomeView[] memory)
  - getPositionView(bytes32 templateId, uint64 epochId, address user) returns (PositionView memory)
  - getTemplateYieldView(bytes32 templateId) returns (TemplateYieldView memory)
  - getOperatorTemplateView(bytes32 templateId) returns (OperatorTemplateView memory)
  - getOperatorGlobalView() returns (OperatorGlobalView memory)

  Optional convenience function if the implementer can do it cleanly:

  - getUserEpochPositionViews(bytes32 templateId, address user, uint256 cursor, uint256 size)
      - wraps getUserEpochs plus epoch/position summaries for UI pagination

  ### Claim-preview logic

  For PositionView:

  - if epoch is not claimable, preview fields should be zero with explicit non-claimable state
  - if refundMode, refund preview should be computed from pos.totalStake
  - if resolved, preview should use the same math path as claim logic in a read-only fashion

  The implementer should reuse existing payout/refund logic rather than invent separate view math.

  ### Yield-view logic

  For TemplateYieldView:

  - if no router is configured, return a clean zeroed snapshot with routerAssigned = false
  - if router is configured:
      - query router read surface
      - compute current ratio from principal/current value
  - if router is disabled or template has unreconciled recovered balance:
      - still return raw values where meaningful
      - mark the snapshot as degraded / recovery-pending

  ### Compatibility

  - keep existing low-level view methods unchanged
  - add new selectors to the view module wiring
  - do not change lifecycle/accounting behavior
  - do not add storage just for chart history in this phase

  ### Core PM view tests

  - getActiveEpochView across open, locked, resolved, voided, canceled states

  Add tests for:

  ### Acceptance criteria

  Implementation is complete when:
  - frontend has sufficient canonical inputs to compute Kalshi-style Pays out x without raw storage access
  - frontend can display per-template current yield state without needing direct router calls
  - operator dashboard can identify paused, disabled-router, halted, and unreconciled-recovery states from dedicated operator views
  - no historical chart persistence is added on-chain in this phase
  ## Assumptions

  - Historical Polymarket-style charts remain an indexer/UI responsibility.
  - Pays out x is intentionally UI-derived only, not returned by the contract.
  - Yield is shown on-chain as a current snapshot:
      - principal
      - current value
      - unrealized yield amount
      - yield ratio
  - Annualized APR/APY stays off-chain.
  - Separate PM-facing and operator-facing view surfaces are preferred, even if implemented inside the same Solidity module.
